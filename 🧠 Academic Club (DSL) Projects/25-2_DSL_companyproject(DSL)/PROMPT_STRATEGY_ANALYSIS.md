# 프롬프트 전략 구현 분석

이 문서는 `app/llm/prompt_templates.py`에서 사용된 3가지 핵심 프롬프트 전략이 어떻게 구현되었는지 설명합니다.

---

## 1. CoT (Chain of Thought) 구현

### 구현 위치
- **파일**: `prompt_templates.py`
- **주요 함수**: `_get_prompt_parts()` (라인 14-175)
- **핵심 코드**: 라인 81-113, 130, 136-150, 173

### 구현 방식

#### 1.1 명시적 추론 단계 요구
```130:130:lattice_task1/app/llm/prompt_templates.py
    <thinking> 태그로 추론 과정을 기술한 후 <result> 태그로 JSON을 출력하세요.
```

프롬프트에서 `<thinking>` 태그로 추론 과정을 먼저 작성하도록 명시적으로 요구합니다.

#### 1.2 단계별 추론 프로세스 정의
특히 **CNT_AMT (계약 총액)** 필드에서 6단계 추론 프로세스를 명확히 정의:

```81:113:lattice_task1/app/llm/prompt_templates.py
      <thinking> 단계에서 다음 [논리적 검증 프로세스]를 반드시 수행하세요 (순서 중요):
      
      **[최우선] 1) 명시 총액 확인: 계약서 전체에서 직접 명시된 총액을 먼저 찾으세요.**
         - 키워드: "계약금액", "계약 금액", "총액", "총 금액", "총 계약금액", "총 공사금액", "총 공급가액", "총 대가", "전체 금액"
         - 영문: "Contract Amount", "Total Amount", "Contract Value", "Total Contract Value"
         - 문맥: "~로 한다", "~로 정한다", "~로 한다" 등의 확정적 표현이 있는 금액
         - 매우 명확한 명시 총액이 있으면 그것을 사용하고, 계산 단계는 생략하세요. (confidence: 1.0, note: "explicit")
      
      2) 변수 추출: 명시 총액이 없을 때만, 일시금(보증금, 선입금 등), 정기지급액, 지급주기(월/분기/반기/연), 계약기간(시작일~종료일) 등 계약서 곳곳에 흩어진 숫자들을 찾아 정리
      
      3) 지급횟수 계산: 정기지급 구조가 있을 때만 수행
         - 계약기간을 개월수로 정확히 계산 (종료일 - 시작일)
         - 지급주기 확인: 일, 주(7일), 월(1개월), 분기(3개월), 반기(6개월), 연(12개월 or 52주) 등
         - 지급횟수 = (계약기간 개월수) / (지급주기 개월수)
         - 예: 36개월 계약, 분기 지급 → 36 / 3 = 12번
         - 주의: 기간이 확정되지 않으면 계산하지 마세요
      
      4) 계산식 작성: 변수들로 총액 계산이 가능한 경우에만 수행
         - 일시금 + (정기지급액 × 지급횟수) 형태만 사용
         - 비율 역산: 보증금이 총액의 N%인 경우에만 역산
         - 숫자와 연산자(+, -, *, /, 괄호)만 포함
         - 여러 계산 방식이 가능하면, 가장 확실한 하나만 선택
         - "또는", "~중 선택", "최소~", "최대~" 같은 불확정 표현이 있으면 null
         - 변수명이나 미확정 값이 포함된 경우 null 반환
      
      5) 검증 및 결과 선택:
         - 명백한 명시 총액이 있으면: 그 값을 사용 (최우선)
         - 명백한 명시 총액이 없고 계산식만 있으면: 계산식 사용
         - 둘 다 없거나 불확실하면: null
         - 명시 총액과 계산 결과가 다르면: 명시 총액 우선, llm_reason에 "CONFLICT: 명시 총액 우선 사용" 명시
      
      6) llm_reason 작성: 각 단계별 결과를 명확히 요약
         - 형식: "1) 명시 총액: [찾음/없음 및 내용] | 2) 변수: [목록] | 3) 지급횟수: [계산 결과] | 4) 계산식: [수식 또는 null] | 5) 검증: [결과] | 6) 최종: [선택한 값 및 근거]"
```

#### 1.3 예제를 통한 CoT 시연
예제에서도 CoT 패턴을 명확히 보여줍니다:

```136:150:lattice_task1/app/llm/prompt_templates.py
    <thinking>
    - 제목: "물품 공급 계약서" (1페이지 상단)
    - 체결일: "계약일: 2024년 1월 15일" → 20240115
    - 시작일: "2024년 2월 1일부터" → 20240201
    - 종료일: "2026년 1월 31일까지" → 20260131
    - 금액 분석:
      1) 명시 총액: 제2조 "본 계약의 총 계약금액은 금 3억원으로 한다" → 300000000 찾음 (최우선)
      2) 변수 추출: (명시 총액 있으므로 생략)
      3) 지급횟수 계산: (명시 총액 있으므로 생략)
      4) 계산식: (명시 총액 있으므로 생략)
      5) 검증: 명시 총액 사용
      6) 최종: 명시 총액 300000000 사용
    - 재계약: "갱신" 표현 없음 → "X"
    - 자동갱신: 조항 없음 → null
    </thinking>
```

### CoT의 효과
- **추론 과정 가시화**: LLM이 어떻게 답을 도출했는지 추적 가능
- **오류 감소**: 단계별 검증으로 실수 방지
- **일관성 향상**: 동일한 프로세스를 따르도록 강제

## 2. XML 태그 구조 (Claude 모델 최적화)

### 구현 위치
- **파일**: `prompt_templates.py`
- **주요 함수**: `_get_prompt_parts()`, `build_full_fields_prompt()`
- **핵심 코드**: 라인 20, 130, 134-170, 173, 222-226, 228-236

### 구현 방식

#### 2.1 계층적 XML 태그 구조
프롬프트는 다음과 같은 XML 태그 구조로 구성됩니다:

```
<instruction>
  ... 지시사항 ...
  <thinking> 태그로 추론 과정을 기술한 후 <result> 태그로 JSON을 출력하세요.
</instruction>

<example>
  <thinking>
    ... 추론 과정 ...
  </thinking>
  
  <result>
    ... JSON 결과 ...
  </result>
</example>

<contract>
  ... 실제 계약서 텍스트 ...
</contract>

위 <contract> 태그의 계약서를 분석하여, <thinking> 태그로 추론 과정을 기술한 후 <result> 태그로 JSON을 출력하세요.
```

#### 2.2 각 태그의 역할

**`<instruction>` 태그** (라인 20-132)
```20:132:lattice_task1/app/llm/prompt_templates.py
    <instruction>
    당신은 한국어 계약서에서 핵심 메타데이터를 추출하는 법률전문가이자 계약 분석가입니다.
    
    추출할 필드 (JSON 키는 영문 고정, 날짜는 YYYYMMDD 형식, 모르는 값은 null):
    ...
    </instruction>
```
- 역할: 전체 작업 지시사항과 필드별 추출 규칙 정의
- Claude 모델이 구조화된 지시를 명확히 이해하도록 도움

**`<example>` 태그** (라인 134-171)
```134:171:lattice_task1/app/llm/prompt_templates.py
    <example>
    <thinking>
    ...
    </thinking>
    
    <result>
    ...
    </result>
    </example>
```
- 역할: Few-shot learning을 위한 예제 제공
- `<thinking>`과 `<result>`의 올바른 형식 시연

**`<contract>` 태그** (라인 222-226)
```222:226:lattice_task1/app/llm/prompt_templates.py
    contract = f"""
<contract>
{contract_text}
</contract>
"""
```
- 역할: 실제 분석할 계약서 텍스트를 명확히 구분
- 입력 데이터와 지시사항을 분리하여 구조화

**`<thinking>` 태그** (요구사항: 라인 130, 예제: 라인 136-150)
- 역할: CoT 추론 과정을 담는 컨테이너
- LLM이 답을 도출하기 전 단계별 사고 과정을 기록

**`<result>` 태그** (예제: 라인 152-169)
- 역할: 최종 JSON 결과를 담는 컨테이너
- 구조화된 출력 형식 강제

#### 2.3 프롬프트 조립
`build_full_fields_prompt()` 함수에서 모든 태그를 조립:

```228:236:lattice_task1/app/llm/prompt_templates.py
    prompt = (
        instruction
        + "\n\n"
        + example
        + "\n\n"
        + contract
        + "\n\n"
        + final_instruction
    )
```

### XML 태그의 효과
- **구조화된 입력/출력**: Claude가 태그를 명확히 인식하고 구분
- **파싱 용이성**: 태그 기반으로 응답에서 `<thinking>`과 `<result>` 부분을 쉽게 추출 가능
- **일관성 보장**: 태그 구조가 출력 형식을 강제하여 일관된 응답 생성

## 3. 계산 분리 로직

### 구현 위치
- **파일**: `prompt_templates.py`
- **주요 함수**: `_get_prompt_parts()` 내 CNT_AMT 필드 정의
- **핵심 코드**: 라인 72-118

### 구현 방식

#### 3.1 계산 단계 분리
계약 총액(CNT_AMT) 계산을 **6단계로 명확히 분리**:

```81:113:lattice_task1/app/llm/prompt_templates.py
      <thinking> 단계에서 다음 [논리적 검증 프로세스]를 반드시 수행하세요 (순서 중요):
      
      **[최우선] 1) 명시 총액 확인: 계약서 전체에서 직접 명시된 총액을 먼저 찾으세요.**
         - 키워드: "계약금액", "계약 금액", "총액", "총 금액", "총 계약금액", "총 공사금액", "총 공급가액", "총 대가", "전체 금액"

         - 계약기간을 개월수로 정확히 계산 (종료일 - 시작일)
         - 지급주기 확인: 일, 주(7일), 월(1개월), 분기(3개월), 반기(6개월), 연(12개월 or 52주) 등

      5) 검증 및 결과 선택:
         - 명백한 명시 총액이 있으면: 그 값을 사용 (최우선)
         - 명백한 명시 총액이 없고 계산식만 있으면: 계산식 사용
         - 둘 다 없거나 불확실하면: null
         - 명시 총액과 계산 결과가 다르면: 명시 총액 우선, llm_reason에 "CONFLICT: 명시 총액 우선 사용" 명시

         - 형식: "1) 명시 총액: [찾음/없음 및 내용] | 2) 변수: [목록] | 3) 지급횟수: [계산 결과] | 4) 계산식: [수식 또는 null] | 5) 검증: [결과] | 6) 최종: [선택한 값 및 근거]"
```

#### 3.2 단계별 우선순위 명시

**1단계: 명시 총액 확인 (최우선)**
- 계산보다 먼저 명시된 총액을 찾음
- 있으면 계산 단계 생략

**2단계: 변수 추출 (조건부)**
- 명시 총액이 없을 때만 수행
- 일시금, 정기지급액, 지급주기, 계약기간 등 추출

**3단계: 지급횟수 계산 (조건부)**
- 정기지급 구조가 있을 때만 수행
- 계약기간과 지급주기로 계산

**4단계: 계산식 작성 (조건부)**
- 변수로 계산 가능할 때만 수행
- 숫자와 연산자만 포함 (변수명 불가)

**5단계: 검증 및 결과 선택**
- 명시 총액 > 계산식 > null 순서로 우선순위 적용
- 충돌 시 명시 총액 우선

**6단계: llm_reason 작성**
- 모든 단계의 결과를 요약하여 기록
- 디버깅 및 검증 용이

#### 3.3 계산 결과 구조화
CNT_AMT는 단순 값이 아닌 구조화된 객체:

```72:79:lattice_task1/app/llm/prompt_templates.py
    - CNT_AMT: 계약 총액 정보 객체.
      **단순 문자열이 아닌, 아래 4개 필드를 가진 JSON 객체로 출력하세요.**
      {
        "value": "수식 문자열 또는 숫자 문자열 (계산 불가능하면 null)",
        "confidence": 0.0 ~ 1.0 사이의 실수 (1.0: 명시적 찾음, 0.9: 확실한 계산, 0.5 미만: 불확실)",
        "note": "상태 코드 (explicit / calculated / uncertain / not_found)",
        "llm_reason": "다음 6단계 분석 결과를 요약: 1) 변수 추출 2) 지급횟수 계산 3) 명시 총액 4) 계산식 5) 검증 6) 결과"
      }
```

- `value`: 계산 결과 또는 null
- `confidence`: 신뢰도 (명시 총액: 1.0, 계산: 0.9, 불확실: <0.5)
- `note`: 상태 코드 (explicit/calculated/uncertain/not_found)
- `llm_reason`: 6단계 분석 과정 요약

### 계산 분리 로직의 효과
- **명시 총액 우선**: 계산 오류보다 명시된 값 신뢰
- **단계별 검증**: 각 단계를 거쳐 오류 감소
- **추적 가능성**: `llm_reason`으로 계산 과정 추적
- **신뢰도 제공**: `confidence`와 `note`로 결과 신뢰성 평가

## 통합 구조

세 가지 전략이 통합된 최종 프롬프트 구조:

```
<instruction>
  [필드별 추출 규칙]
  [CNT_AMT의 6단계 계산 프로세스]
  <thinking> 태그로 추론 과정을 기술한 후 <result> 태그로 JSON을 출력하세요.
</instruction>

<example>
  <thinking>
    [CoT 추론 과정 시연]
    [6단계 계산 프로세스 시연]
```
