## 처리 순서

레코드 하나당 아래 순서로 적용된다. **순서가 중요하다** — 특히 0번(전면 박스 제거)을
3번(우선 조건) 계산 *전에* 해야 정확하다.

### 0. 전면 박스 제거 (`strip_giant`, uncovered_ocr 계산보다 먼저 수행)

`unified_layout` 레코드에서 페이지 면적의 `--strip_giant_area`(기본 **0.85**) 초과를 덮는
`<div data-bbox="..." data-label="...">...</div>` 블록을 통째로 삭제한다.

- **왜 필요한가**: 라벨러가 실패하면 페이지 전체를 덮는 더미 박스(`0 0 1000 1000`)를
  `Picture` 또는 `Page-footer`로 채워 넣는 경우가 있다. 이 박스가 남아 있으면 페이지의
  모든 OCR을 "덮은 것"처럼 만들어 3번(`uncovered_ocr`) 필터를 무력화시킨다.
- **실측**: 168개(레코드 168건, train 기준)가 이 조건에 해당했고, 그중 144개가 정확히
  좌표 `0 0 1000 1000`이었다. 내부에 중첩 `<div>`가 없고 내용도 비어 있거나
  `<p>Page 53 of 73</p>` 수준이라 블록 단위 삭제가 안전하다고 판단했다.
- **표 crop 은 대상 아님**: `prompt_style != unified_layout`인 레코드는 건드리지 않는다.
  표 crop 의 `Table` bbox 는 원래 페이지의 90% 이상을 덮는 게 정상이라(중앙값 0.921)
  같은 기준을 적용하면 멀쩡한 표가 통째로 날아간다.
- 삭제 후 `gt_html`에 `data-bbox` 블록이 하나도 안 남으면 `empty_after_strip` 사유로
  별도 제거된다(실측 2건, 전면 박스가 그 문서의 유일한 라벨이었던 경우).

### 1. `tiny_table_bbox` — 표 crop의 Table bbox 조각

`reference_16886` 소스이고 파일명이 `T숫자...` 또는 `nested*`인 표 crop 레코드만 대상.

판정(둘 중 하나라도 걸리면 제거):
- 가장 큰 bbox의 면적(페이지 대비) `< --tiny_area`(기본 **0.10**)
- 위 조건을 통과해도, bbox 최대 면적 ÷ OCR 텍스트 분포 영역(min/max로 만든 bounding box)
  면적 `< --tiny_cover`(기본 **0.50**)

**왜**: 라벨러가 표 영역이 아니라 페이지 구석 조각(페이지번호 등)을 Table bbox로 잘못
잡은 케이스. 실측 예시: `T04_C06_50008_1004_175.jpg`의 bbox가 `908 0 979 14`(면적
0.001)인데 OCR은 페이지 전체(89개)에 퍼져 있었다.

- 실측 분위: 표 6,000건 중 면적 1%=0.631, 5%=0.802, 중앙값=0.921. `< 0.10`은 최소 8건이
  0.005 미만이고 그다음이 0.178이라 그 사이 공백을 이용해 잡은 값이다.

### 2. `short_ocr` — OCR이 거의 없는 new_63541 페이지

`new_63541` 소스만 대상. `ocr_info`의 `text` 필드 총 글자수 `<= --min_chars`(기본 **100**)
이면 제거. 텍스트가 거의 없는(빈 페이지·이미지 위주) 문서라 레이아웃 학습 가치가 낮다고
판단.

### 3. `uncovered_ocr` — 라벨 박스가 OCR 텍스트를 못 덮는 비율

**"OCR은 글자를 잡았는데 라벨 박스가 그걸 안 덮는다" = 라벨 누락**을 직접 재는 지표다.

```
uncovered = area( OCR_박스_합집합 AND NOT 라벨_박스_합집합 ) / area( OCR_박스_합집합 )
```

`raster()`로 0~1000 좌표를 250×250 불리언 마스크에 그려 합집합을 계산한다(겹침 중복
계산 방지). `uncovered > 임계값`이면 제거.

- **임계값은 소스별로 다르다**: `new_63541`은 `--max_uncovered_new`(기본 **0.05**),
  `reference_16886`은 `--max_uncovered`(기본 **0.10**). new 쪽이 라벨 누락이 더 잦다는
  육안 검수 결과를 반영해 더 엄격하게 잡았다.
- **왜 0이 아닌가**: 정상 문서도 OCR은 글자에 딱 붙고 레이아웃 박스는 블록 단위라 경계에서
  어긋난다. 실측 중앙값이 `new_63541` 0.023, `reference_16886` 0.053이라, 0을 기준으로
  하면 거의 전량이 제거된다(임계값별 실측표 참고).
- **표에도 적용된다**(레이아웃 전용이 아님). 다만 이 지표를 도입하기 전 시도했던
  "bbox합집합/OCR합집합 비율" 방식은 표 crop에서 구조적 오탐이 났다 — 밀집 표는 OCR
  박스가 표 전체를 타일처럼 덮어 비율이 1.0 근처로 나와, 정상 표(`nested_000030.jpg`,
  bbox `19 48 980 937`)가 오검출됐다. `uncovered_ocr`(못 덮은 몫을 직접 계산)로 바꾸고서야
  이 오탐이 사라졌다.

**임계값별 실측(레이아웃 레코드, 3-split 합산, 참고용)**

| 임계값(초과 시 제거) | new_63541 | reference_16886 |
|---|---:|---:|
| > 0 (조금이라도) | 94.5% | 97.7% |
| > 0.02 | 52.7% | 78.5% |
| > 0.05 (new 채택값) | 30.8% | 52.3% |
| **> 0.10 (reference 채택값)** | 11.0% | **17.6%** |
| > 0.20 | 2.3% | 2.1% |

### 5. `irregular_table_shape` — new_63541 표의 비사각형 구조

`new_63541` 소스이고 `prompt_style == unified_layout`이며 `gt_html`에
`data-label="Table"`이 있는 레코드만 대상(즉 레이아웃 페이지 안에 박힌 표. `reference_16886`
의 표 crop 태스크는 대상 아님 — 그쪽은 crop 자체가 표 하나라 위 1번으로 이미 검증됨).

`table_shape_irregular()`가 `<table>`마다 **rowspan을 반영한 행별 실효 폭**을 계산한다.

```
실효폭(행) = 그 행 자신의 colspan 합 + 위 행에서 rowspan 으로 아직 내려오고 있는 칸 수
```

정상 표는 이 값이 모든 행에서 동일해야 한다(표 전체 폭). 최빈값(mode)과 다른 행이 하나라도
있으면(폭이 넓어지든 좁아지든) `irregular_table_shape`로 제거한다.

- **rowspan을 반영해야 하는 이유**: 단순히 "행별 colspan 합"만 보면, rowspan으로 인해
  정상적으로 좁아지는 행(위 행의 셀이 아래로 이어지는 중이라 이번 행엔 셀이 적은 경우)을
  오탐한다. `active` 리스트로 아직 소모되지 않은 rowspan을 추적해 이를 보정한다.
- **튀어나옴(over)과 좁아짐(under) 둘 다 잡는다.** 처음엔 "튀어나옴"만(단순 colspan 합
  기준) 봤을 때 449장이 걸렸는데, rowspan을 제대로 반영해 재보니:
  - 완전 사각형 3,171 Table 블록
  - 튀어나옴만 226개 블록(문서 244장)
  - 좁아짐만(rowspan으로 설명 안 되는 진짜 결손) 304개 블록(문서 319장)
  - 둘 다 55개 블록
  - **합집합 492장/2,663장(18.5%)** — 이 결과를 보고 좁아짐도 포함하기로 확정.
- **실측 예시**:
  - 좁아짐: `[불명확한 표인식]KDRG V4.5 분류집_page_935.png` (파일명 자체에 "불명확한
    표인식"이 있음), `삼성전자_분기보고서(2025.11.14)_page_134.png`(폭 14가 계속되다
    뒤쪽 3개 행만 13으로 한 칸 모자람), `92873_...kb액티브배당증권..._`(폭 9가 계속되다
    한 행만 5로 뚝 떨어짐 — 셀 누락 의심)
  - 튀어나옴: `위임전결규정 시행세칙(2025. 2. 6. 개정)_page_028.png`(mode 7인데 전체가 8),
    `2024년도부산광역시정보화시행계획_page_041.png`(대부분 5인데 2개 행만 6)

### 4. `invented_ellipsis` — 원본에 없는 말줄임을 라벨이 임의 생성

`gt_html`에 말줄임(정규식 `\.{3,}` 또는 `…`)이 있는데, 같은 레코드의 `ocr_info` 텍스트를
전부 이어붙인 문자열에는 말줄임이 전혀 없으면 제거.

- **판정 세부**: 말줄임 위치 직전 200자 안에 `<td` 또는 `<th`가 있으면
  `invented_ellipsis:table`, 아니면 `invented_ellipsis:text`로 기록한다(제거 자체는 둘 다
  동일하게 처리, 사유만 구분).
- **왜**: OCR이 실제로 읽은 텍스트에 없는 "..." 를 라벨이 만들어냈다면, 모델이 원문을
  임의로 축약하도록 학습시키는 셈이다. 표 안의 셀에서 특히 유해하다(숫자·항목이 실제로
  잘려나가는 것과 같은 효과).
- `--no_ellipsis_filter`로 끌 수 있다.

## 알려진 한계 / 참고

- 필터는 전부 규칙 기반이라 오탐이 없지는 않다. `uncovered_ocr` 도입 전에 시도했던
  "bbox합집합/OCR합집합 비율" 방식은 육안 검수 결과 레이아웃에서 걸린 건 중 실제
  라벨 누락으로 교차검증된 게 약 1%뿐이었다(대부분은 박스를 텍스트에 딱 붙여 라벨링한
  스타일 차이). 현재의 `uncovered_ocr`(못 덮은 영역을 직접 계산)로 바꾼 뒤에도 완벽한
  정밀도를 보장하지는 않으므로, 학습 결과가 기대와 다르면 이 문서의 임계값부터 재검토할 것.
- `irregular_table_shape`는 `new_63541`에만 적용했다. `reference_16886`의 레이아웃
  페이지 안에 박힌 Table 블록에는 적용하지 않았다(그쪽은 표 crop 태스크의 검증을 이미
  거쳤다는 전제였으나, 레이아웃 페이지 내 삽입 표까지 같은 검증을 거친 것은 아니다 —
  필요하면 조건 5의 소스 조건만 빼서 재실행 가능).
- 임계값(0.05/0.10, 0.85 등)은 전부 실측 분위수를 참고해 사람이 정한 값이다. 데이터
  분포가 바뀌면(예: 소스 추가) 재검토가 필요하다.
